01The model, and what it cannot hold

The stock is not a solid. It is a rectangular grid of height samples — one number per grid vertex, saying how far down the material has been cut at that exact (x, y). Two typed arrays hold everything:

heights: new Float32Array((nx + 1) * (ny + 1)),
// Strict shadow of `heights`: operation index + 1, 0 for uncut.
cutIds:  new Uint16Array((nx + 1) * (ny + 1)),
rebuildStock()

A sample's index is hi = gy * (nx + 1) + gx, and its world position is (minX + gx·cellX, minY + gy·cellY). Everything else in the simulation — the mesh, the colours, the material-removed readout — is derived from those two arrays.

Cutting only ever lowers a height. That single property is what makes the whole thing cheap: playing the program forward is incremental, because a new move can only push samples further down. It is also why scrubbing backwards cannot be undone move by move — the height map has forgotten what used to be there, so the only way back is to refill the block and re-cut from the start.

The cost is expressive: one height per column means no undercuts, no overhangs, and no side-facing walls. A vertical wall in the model is not a wall at all — it is a steep quad spanning one cell, between a sample that got cut and its neighbour that did not.

02Sizing the block

Three things fix the block: its Z extent, its XY footprint, and how finely that footprint is sampled.

Top and bottom

The suggested top is the shallowest depth a cutting move actually reaches: for each non-rapid segment, take the lower of its two Z values, then take the maximum across segments. Purely vertical feed moves are excluded, because a lead-in plunge descends through free air and lands wherever its operation happens to start — on a multi-tool file the deepest-starting tool would otherwise set the top and invent a layer of material that was never there.

Footprint

The XY comes from cutFootprint — the extent of cutting moves only, not rapids — expanded by the margin on each side. The margin may be negative, meaning the block starts inside the toolpath and the outer passes machine its sides away. The only thing not honoured literally is a margin deep enough to invert the footprint:

shortest = min(sizeX, sizeY)
floor = −0.5·shortest + max(0.01·shortest, 1e−3)
margin = max(typed, floor) // leaves a sliver

Grid

The resolution setting is a count of cells along the longest side. Both axes then take the same target cell size, so cells come out square-ish rather than stretched:

limit = min(2000, (maxTextureSize − 1) / 2)
target = max(sizeX, sizeY) / cells
nx = clamp(round(sizeX / target), 1, limit)
ny = clamp(round(sizeY / target), 1, limit)
cellX = sizeX / nx cellY = sizeY / ny

target is set from the longest side, so neither axis can exceed cells on its own; the limit is what the hardware will actually hold. The colour texture is 2·ny + 1 texels tall, which runs into MAX_TEXTURE_SIZE well before the height map's nx + 1 does — hence the halving. The 2000 on top of that is a budget for the display mesh, not a limit of the carve.

Where the memory goes Not where you would expect. The simulation itself is the cheap half: a 32-bit depth texture and a cut-id texture at one texel per sample, plus the colour map. What costs is the mesh that displays it, and within that the index buffer — 96 MB of the 160 MB at Maximum, six Uint32 indices per cell. It is written once at build time and never touched again, which is the trade the fixed-topology mesh in §6 is making; it is also why the resolution ceiling is where it is. Getting past it means generating the surface grid procedurally rather than storing it, not making the carve any cleverer.

03The cutter as one function

Every tool the simulation supports is a solid of revolution, so its whole geometry collapses to a single scalar function: the height of the cutting surface above the tip, at radial distance d from the axis.

function toolHeightAt(tool, d) {
    if (d <= tool.flatRadius) return 0;
    const k = d - tool.flatRadius;
    if (tool.isCone) return k * tool.invTanWall;
    return tool.cornerRadius - Math.sqrt(Math.max(tool.cr2 - k * k, 0));
}

flatRadius (written f below) is what unifies the four profiles: it is the radius of the tool's flat bottom. The full radius for a flat end mill, zero for a ball nose, r − cornerRadius for a bull nose, and the tip flat for a cone.

h(d) = 0 for d ≤ f
h(d) = (d − f)·cot θ cone, θ measured from the axis
h(d) = Rc − √(Rc² − (d − f)²) ball / bull, corner radius Rc

Two properties of h matter downstream, and everything in §4 leans on them:

  • h(0) = 0 for every profile. The tip is the tool's lowest point, so the G-code Z is the tip — no per-profile offset anywhere in the carve.
  • h is continuous and non-decreasing. The profile only ever rises as you move outward from the axis. This is the property that lets a whole swept move be resolved with one evaluation per sample.

One trap in the file format CAM posts write TAPER= under two different conventions. A drill's 118° and a spot drill's 90° are included tip angles and must be halved; a chamfer mill's 45° is measured from the axis and is already the half angle. coneHalfAngle() resolves which by family — read a 90° spot drill as a half angle and you get a tip with no height at all.

04The capsule sweep

This is the core of the simulation. Arcs have already been flattened into chords upstream (to a 0.005 mm sagitta tolerance), so the carve only ever sees straight moves.

Take a move from A to B with the tip held at height z. In plan view, the region the tool passes over is a capsule: every point within r of segment AB. For each height sample p inside it, we need the lowest the tool's surface ever gets above that sample over the whole move.

Closest approach

Project p onto the axis and clamp to the segment:

d = B − A
t = clamp( ((p − A)·d) / |d|², 0, 1 ) // t = 0 if |d|² = 0
e = p − (A + t·d)
dist² = e·e // skip the sample if dist² > r²

Clamping t to [0, 1] is what turns the infinite line into a segment and the slab into a capsule: outside the ends, the nearest point on the axis is an endpoint, which gives exactly the rounded caps.

Why one evaluation is enough

Over the sweep, the tool's surface sits at height z + h(dist(t)) above the sample. We want the minimum over t. Because h is non-decreasing (§3), minimising h(dist(t)) is the same as minimising dist(t) — so:

mint [ z + h(dist(t)) ] = z + h( mint dist(t) ) = z + h(distmin)

The closest approach is the whole answer. For a constant-Z move this is exact, however long the move is — there is no stepping along the path, no accumulated error, and the cost per sample is one dot product, one clamp, one distance and one profile evaluation.

The inner loop

let t = lenSq > 0 ? ((px - x0) * dx + (py - y0) * dy) / lenSq : 0;
if (t < 0) t = 0; else if (t > 1) t = 1;

const ex = px - (x0 + t * dx);
const ey = py - (y0 + t * dy);
const distSq = ex * ex + ey * ey;
if (distSq > r2) continue;

// A flat end mill has flatSq === r2, so it never reaches the sqrt.
let target = distSq <= flatSq ? z : z + toolHeightAt(tool, Math.sqrt(distSq));
if (target < stockBottom) {
    target = stockBottom;
    stockAnyThroughCut = true;
}

const hi = rowBase + gx;
if (heights[hi] > target) {
    heights[hi] = target;
    cutIds[hi] = cutId;
    changed = true;
}
carveCapsule()

Three details worth keeping:

  • if (z >= stock.top) return false guards the whole function. Since h(0) = 0, the tip is the lowest point of the tool, so a tip above the stock top cannot remove anything.
  • Everything stays squared until the last possible moment. A flat end mill never takes a square root, because flatSq === r2 makes the first branch always true.
  • Reaching the floor sets stockAnyThroughCut. That flag gates an entire per-cell pass later (§7) — until something goes clean through, there is no hole to open and the pass is skipped.

05Following a changing Z

A capsule covers the full XY sweep of a move exactly, however long it is. Slicing is therefore needed for one reason only: a move whose Z changes — a ramp, a plunge, a helical arc. The tolerance is the model's own resolution:

zTol = min(cellX, cellY)
slices = clamp( ceil(|Δz| / zTol), 1, 4000 )

If |Δz| ≤ zTol the move is carved as a single capsule and no slicing happens at all. Otherwise each slice is a capsule over its own sub-segment, cut at min(z₀, z₁) — the deepest Z the slice reaches.

Taking the minimum is deliberately conservative: within a slice, the simulation removes slightly more than the real cutter would, never less, and the over-removal is bounded by zTol — one cell. So the Z error and the XY error are the same size, both set by the resolution slider, and neither can be tightened without the other.

06One mesh, moving vertices

The mesh is built once per stock rebuild and never rebuilt while cutting. Its topology is fixed — only vertex Z values change — so the index buffer, the UVs and the normals attribute are all written a single time.

The walls — the skirt — hang from the boundary samples. Each wall vertex pair is stored alongside the height sample it follows, so a refresh is two flat loops with no arithmetic:

for (let i = 0; i < stock.topCount; i++) {
    pos[i * 3 + 2] = heights[i];
}
for (let k = 0; k < skirt.length; k += 2) {
    pos[skirt[k] * 3 + 2] = heights[skirt[k + 1]];
}
attr.needsUpdate = true;

The position attribute is marked DynamicDrawUsage, since it is re-uploaded on every carve. Nothing else in the geometry is.

Material removed

The readout is the mean drop across all samples, as a fraction of the block's Z span:

removed % = 100 · Σ(top − hi) / ( N · (top − bottom) )

This weights every sample equally, which slightly over-weights the boundary rows compared with a true volume integral over cells. At 500 cells the discrepancy is a fraction of a percent — it is a progress indicator, not a metrology result.

07Colour, and the hole problem

Every surface in the block is tinted by the operation or tool that made it. The obvious implementation — a vertex colour attribute — is wrong here: colours interpolate across a triangle, so every boundary between two operations came out as a gradient smeared over a whole cell. Duplicating vertices per face would fix that, but at six vertices per cell the position buffer, rewritten on every carve, grows sixfold.

The answer is a nearest-filtered texture with one texel per cell. Surface vertex (gx, gy) gets UV (gx/nx, gy/texRows) — exactly on the texel boundary — so every fragment of a cell's quad reads the same texel and the quad is one flat colour, with colour changes landing precisely on cell edges.

Three bands

The texture is nx wide and 2·ny + 1 tall, in three bands that exist for three different reasons:

Which cut owns a cell

A cell has four corner samples and one texel, so it has to choose. The deepest corner wins — on a steep wall quad that is the sample at the foot of the wall, the one the cut actually reached, so the face carries the colour of the tool that made it. Ties go to the higher cut id, which is the later operation, so a boundary between two passes does not drift into whichever corner the scan happened to visit first.

Cut ids are opIndex + 1, leaving 0 for uncut. 0xffff is reserved for a rapid that removed material — a gouge — which sorts above every real id and so wins every tie, and is painted red in every colour mode including Uniform.

Opening a hole

A height map cannot describe a void. A cell cut clean through does not vanish; it sits at the bottom of the block, coplanar with the underside, leaving a paper-thin membrane closing what should be an opening. The fix is alpha plus alphaTest: 0.5:

throughLevel = bottom + max( (top − bottom)·1e−5, 1e−9 )
alpha = ( max of the cell's four corners ≤ throughLevel ) ? 0 : 255

The highest corner decides, because that is the one still holding material up. The same alpha is written twice — once to the surface texel and once to its shadow in the bottom band — so the hole opens from above and below together. The epsilon exists because the heights are Float32 and stock.bottom is not.

Why the modes are free Uniform, By Tool and By Operation are all views of the same cut ids, which the carve records whatever the mode happens to be. The mode lives in a colour table of a few dozen texels, one per id; switching mode rewrites that table and repaints. It is never a re-cut.

08The frame loop

Carving is driven from the animation frame, not from input events. requestCarve(dist) only sets a pending value; the loop consumes at most one carve per frame. Dragging the progress slider — which can force a replay of the whole program on every pointer move — therefore costs one carve per frame rather than one per event.

What the CPU does per frame is now only bookkeeping. carveTo walks the segments it has not reached yet and turns each one into capsules — one per constant-Z sweep, more where the Z is ramping — writing ten floats each into a staging buffer of 65,536. When that buffer fills it is uploaded and drawn, and filling starts again. Nothing else on the CPU touches the stock: the height map, the cut ids and the colour texture are all GPU-side.

The height map is the depth buffer

The carve pass draws one quad per capsule, sized to exactly the grid samples that capsule can reach, into an offscreen target whose depth attachment is the height map. Each fragment works out its own sample's distance from the swept tool axis, raises the tool's tip height by the profile at that distance, and writes the result as its depth. Then the depth test — set to strictly less, not the default less-or-equal — does the rest:

if (heights[hi] > target) { heights[hi] = target; cutIds[hi] = cutId; }
what the depth unit now does

The comparison, the minimum and the write are one fixed-function operation. The cut id rides along in the colour attachment, and lands only when the depth test passed — which is what keeps it a shadow of the height rather than an accumulator, tie included: an equal target fails a strict less-than and leaves the earlier id standing.

Why batching is safe The final depth is the minimum over every capsule, whatever order they were drawn in and however they were split across draws. The id that survives belongs to the first capsule, in draw order, to reach that minimum. So streaming a program through a 65,536-capsule buffer gives bit-identical results to one impossible draw of all of it — which is what makes a fixed, small buffer enough for a file of any size.

Two consequences worth naming. The mesh's vertex Z is read from that depth texture in the vertex shader, so the position buffer is written once when the block is built and never again — the surface changes with no upload at all. And nothing can be read back: WebGL cannot return a depth attachment to the CPU, so the simulation is write-only. The single exception is the gouge key, which is one bit, reduced on the GPU to one texel before it is read.

Inside carveTo, each segment contributes only the arc-length interval that the new distance actually covers. Those bounds are converted back into parameters along the segment and handed to the sweep:

const a = Math.max(carvedDistance, seg.startDist);
const b = Math.min(dist, segEnd);
const t0 = (a - seg.startDist) / seg.length;
const t1 = (b - seg.startDist) / seg.length;
carveTo()

So a segment that is half-traversed carves exactly its first half, and picks up from there on the next frame. carveSegIndex only advances past a segment once it is fully consumed.

09Where the model runs out

The height map's single limitation propagates everywhere, and it is worth naming precisely: one height per column, so no surface can face sideways.

The sharpest case is a pass that runs along or past the outer boundary. In reality the cutter removes a slab from the edge and leaves a machined wall set in from the original face. The height map cannot hold that: it can only drop the boundary sample. The material below that sample — which is what the outside of the block actually shows — is never touched by anything.

Fixed — the skirt colouring bug Wall vertices used to borrow the UV of the boundary sample they follow. When a pass ran along the edge, that sample's texel took the cut colour, and the whole outside face of the block was painted in it from the cut depth down to the underside. It is now read from the spare texture row, so the walls stay uncut stock. The wall the cut really made is the steep surface quad just inboard, and that one is still coloured by the pass that made it.

The rest of the envelope

  • Arcs are chords. Flattened upstream to a 0.005 mm sagitta, so the carve never sees curvature — a chord count derived from the radius, not a fixed number.
  • The tool is a solid of revolution. No flutes, no helix, no runout; a rotating cutter is fully described by its silhouette.
  • Three axes. The tool axis is always +Z. Tilt, rotary work and 5-axis motion are outside the model entirely.
  • No mechanics. Deflection, chatter, and material spring-back do not exist here. This answers what shape is left, not what the machine will actually do.
  • Resolution couples XY and Z. One slider sets the cell size, and the Z slicing tolerance is min(cellX, cellY), so the two errors always move together.
